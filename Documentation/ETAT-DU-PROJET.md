# VIGIE HSE — État du projet

Document de référence. Objectif : permettre à **n'importe qui** — la collectivité, un développeur humain qui découvre le projet, ou une future session d'IA (Claude ou autre) — de reprendre ce projet sans avoir suivi les échanges qui l'ont produit.

Dernière mise à jour de ce document : voir date de dernière modification du fichier. Version active du projet au moment de la rédaction : **V0.1.1.2**.

---

## 1. Le projet en une phrase

Un dashboard HSE (Hygiène-Sécurité-Environnement) "VIGIE HSE" pour une collectivité territoriale (Ville de Verchamps + Agglomération de Verchamps), couvrant le registre AT/MP, le Document Unique (DUERP), et une suite d'outils de prévention connexes — construit comme un **prototype fonctionnel sans backend**, pensé pour être démontré/testé localement avant tout raccordement à une vraie base de données.

## 2. Ce que ce n'est PAS

- **Pas d'application de production** : aucune authentification réelle (mots de passe en clair, comparaison côté client), aucune base de données serveur, aucune API. Tout vit dans le `localStorage` du navigateur de chaque utilisateur.
- **Pas synchronisé entre utilisateurs** : deux personnes ouvrant l'app sur deux machines différentes ne voient pas les mêmes données saisies — chaque navigateur a sa propre copie locale.
- **Ne pas déployer tel quel en ligne** pour un usage réel avec des données d'agents (RGPD). C'est un démonstrateur d'ergonomie, d'architecture fonctionnelle et de modèle de données, à faire reprendre par une vraie stack (backend + base de données + authentification) avant mise en production réelle.

## 3. Stack technique

- **HTML/CSS/JavaScript vanilla**, aucun framework (pas de React/Vue), aucune étape de build, aucun bundler. Chaque page est un fichier `.html` autonome (CSS et JS inline dans le même fichier).
- **Persistance** : `localStorage` (données) + `sessionStorage` (session de connexion).
- **Import/export Excel** : [SheetJS](https://sheetjs.com/) (`assets/xlsx.full.min.js`, version `0.18.5`, licence Apache-2.0 — copie à l'identique de celle de cdnjs, embarquée le 2026-09-25 pour que l'import et l'export marchent sans Internet ni accès au CDN, sur le poste d'un utilisateur).
- **Polices** : Barlow Condensed (titres), IBM Plex Sans (texte courant), IBM Plex Mono (chiffres/données) — **embarquées** dans `assets/polices/` depuis le 2026-09-29 (jeu « latin », licence SIL OFL 1.1 dans `LICENCES-POLICES.txt`) : chaque page charge `<link rel="stylesheet" href="assets/polices/polices.css">`, **jamais Google Fonts** (qui recevait l'adresse IP du poste à chaque page). Une nouvelle page reprend cette balise ; une graisse nouvelle s'ajoute à `polices.css` avec son fichier.
- **Icônes** : sprite SVG artisanal inline (`<symbol id="i-...">`) dans chaque page, pas de bibliothèque externe.
- Navigation entre pages : simples liens `<a href="...">`, pas de routeur.

### Pourquoi cette stack ?

Décision volontaire pour rester démontrable immédiatement (double-clic sur un `.html`, aucune installation) et itérable très vite avec une IA en pair-programming. Le jour où le projet passe en vraie production, cette architecture devra être portée vers une vraie stack (voir section 9, "Prochaines étapes techniques").

## 4. Comment lancer / tester le projet

**Ouvrir directement les fichiers `.html` du dossier de la version active (`V0.1.1.2`) dans un navigateur** (double-clic, ou `file://...`). Pour des données partagées entre onglets, navigateurs et comptes de ce poste : `node serveur/serveur.js` puis http://localhost:8780 (serveur local, `PLAN-MISE-EN-PRODUCTION.md` §4 bis). Ne PAS passer par un lien hébergé de type Artifact/Claude — Cloudflare bloque l'accès à `localStorage` dans ce contexte, ce qui casse toute la persistance (bug rencontré et documenté durant la construction du projet).

Comptes de test (voir aussi §7) :

## 5. Arborescence des versions

```
Projet HSE/
├── V0.1/              ← version originale figée (module Registre AT/MP seul, look "Jarvis" sombre)
├── V0.1.1/             ← 1ère refonte visuelle "HSE Soft Tech" (pastel, sidebar+topbar), même périmètre fonctionnel que V0.1
├── V0.1.1.1/           ← + authentification par rôles (admin/manager), panneau Administration, cockpit (météo, actus), Plan d'Actions, Santé & Visites
├── V0.1.1.2/           ← ACTIVE. Stabilisations + Registre Santé & Sécurité (RSST) + Vérifications Périodiques + widgets météo/score dans la topbar + actus secteur sourcées
├── future modules.txt  ← notes brutes de l'utilisateur (backlog) — voir Documentation/ROADMAP-MODULES-FUTURS.md pour la version organisée
└── Documentation/      ← ce dossier
```

**Règle suivie tout du long : chaque nouvelle version doit conserver 100% des capacités de la précédente ("zéro régression").** Ne jamais retirer une fonctionnalité existante sans que l'utilisateur le demande explicitement.

Chaque version est un dossier autonome et complet (pas de dépendance croisée). Pour repartir d'une nouvelle itération majeure, copier le dossier de la version active vers `V0.1.1.3` (ou la convention `X.Y.Z` suivante) plutôt que d'éditer `V0.1.1.2` pour des changements très structurants — garder `V0.1.1.2` comme un point de restauration fiable tant qu'une nouvelle version n'est pas validée.

### 6 bis. Composant partagé `assets/tri-filtres.js` (tri & filtres de colonne)

Jusqu'ici chaque page était strictement autonome (CSS et JS en ligne, dupliqués). Ce composant est la **première exception assumée** : le chantier « tri & filtres façon Excel » devait être construit une seule fois plutôt que dupliqué sur chaque page à tableau.

Il reste compatible avec les contraintes du projet : script classique (pas de module ES), donc il fonctionne aussi bien en `file://` qu'en HTTP, sans étape de build ni dépendance. **Il injecte lui-même sa feuille de style**, construite sur les variables CSS déjà définies par chaque page (`--surface-el`, `--border`, `--accent`…) — il suit donc automatiquement le thème clair/sombre sans fichier CSS partagé à maintenir.

**Pour l'ajouter à une page :**
```html
<script src="assets/tri-filtres.js"></script>
```
```js
const tri = VigieTri.create({
  columns: VISIBLE_COLUMNS.map(c => ({ key:c.key, label:c.label, noFilter:!!c.noFilter, value:COLUMN_VALUES[c.key] })),
  onChange: () => render(),
});
tri.decorate($("theadFields"));   // après chaque (re)construction de l'en-tête
rows = tri.apply(rows);           // dans render(), après les filtres globaux de la page
tri.reset();                      // à câbler sur le bouton "Réinitialiser" de la page
```

- `value(row)` est **optionnel** : par défaut le composant lit `row[key]`. Il faut le fournir pour toute colonne dont la valeur affichée est calculée (badge, champ dérivé) — on trie et on filtre toujours sur la **valeur métier, jamais sur le HTML rendu**. Exemple dans `registre-at-mp.html` : la constante `COLUMN_VALUES` couvre `arretStatut` et `joursArret`.
- `noFilter:true` neutralise une colonne (utilisé pour la colonne Actions).
- Comportements repris du tableur : tri à 3 états (croissant → décroissant → annulé), tri numérique ou texte français détecté automatiquement, **valeurs vides toujours en fin quel que soit le sens**, filtres cumulés en ET, et options d'une colonne calculées sur les lignes filtrées par les *autres* colonnes (une colonne filtrée conserve toutes ses propres options).
- **Déployé sur les 10 pages à tableau** (2026-09-14) : `registre-at-mp.html`, `document-unique.html`, `plan-actions.html`, `registre-sst.html`, `verifications-periodiques.html`, `produits-chimiques.html`, `formation-habilitation.html`, `sante-visites.html`, `inspection-audit.html`, et `epi-dotation.html` (4 tableaux, donc 4 instances indépendantes). Le tableau de cotation du DUERP, qui est une référence statique, n'est volontairement pas équipé.
- **Deux formes d'intégration** selon la page : `registre-at-mp.html` génère ses en-têtes en JS (on lui passe `VISIBLE_COLUMNS`, et `decorate()` est rappelé à chaque reconstruction de l'en-tête) ; les neuf autres ont un `<thead>` écrit en dur (on ajoute un `id` sur la ligne d'en-têtes et on déclare la liste ordonnée des colonnes à la main). **Dans les deux cas, l'ordre déclaré doit suivre exactement celui des `<th>`** — un décalage trierait silencieusement la mauvaise colonne, sans erreur visible. Vérifier après toute modification d'en-tête.
- ⚠️ **Cache navigateur** : GitHub Pages sert ce fichier avec `max-age=600`. Après une modification, un visiteur peut donc garder l'ancienne version jusqu'à 10 minutes (les pages HTML ont la même politique). En test, forcer un rechargement dur pour ne pas déboguer une version périmée.

## 7. Modèle de droits — profils (depuis le 2026-10-01)

**Un compte reçoit un ou plusieurs profils ; ses droits sont le niveau le plus haut de chacun, module par module.** Fini les quatre rôles codés en dur (`admin` / `rh` / `manager` / `ag`) et les permissions ajoutées module par module : tout vit dans `assets/droits.js` (`VigieDroits`, le même fichier pour les pages et pour le serveur) et s'édite dans Administration → **Profils**. Les droits ne s'éditent que sur les profils ; la fiche d'un compte porte ses profils (`u.profils`, liste d'identifiants), ses services (`u.services` : `["*"]` ou une liste — **tout compte** peut maintenant être limité à certains services, plus seulement le manager), `u.anonymise` et `u.active`.

**Niveaux.** Chaque module a une liste ORDONNÉE de niveaux ; un niveau inclut les précédents, et « aucun » est toujours le plus bas (il n'est pas rappelé dans le tableau). Catalogue (`VigieDroits.MODULES`, dans l'ordre du menu) :

| Module (identifiant) | Niveaux (du plus bas au plus haut) | Pages / registres |
|---|---|---|
| `atmp` Registre AT/MP | consulter · déclarer · gérer | registre-at-mp, saisie-rh, tableau de bord (mini-tableau) ; `dataset`, `rh_log` |
| `rsst` Registre SST | déposer · déposer et voir les auteurs · répondre et clôturer | registre-sst ; `rsst` |
| `duerp` Document unique | consulter · gérer | document-unique, saisie-duerp ; `duerp_dataset`, `duerp_log` |
| `produits`, `actions`, `sante-visites`, `verifications`, `inspections`, `formations`, `epi`, `penibilite`, `atmp-admin`, `accident-analyse`, `urgences`, `gestion-rh`, `entreprises-ext`, `accueil-poste` | consulter · gérer | la page du même nom ; leurs registres |
| `documentation` Base documentaire | consulter · rédiger | base-documentaire ; `wiki`, `documents`, `doc_types` |
| `dialogue-social` | consulter · participer (représentant) · direction (répondre, clôturer) | dialogue-social ; `ds_*` |
| `reporting` | consulter | reporting |
| `administration` | gérer | administration ; comptes, profils, référentiels, Flash Info, veille, journal d'audit, effacement général, consultations |

**Profils préréglés** (identifiants stables, renommables, droits modifiables, jamais supprimés — la graine est fusionnée clé par clé sous ce qui est enregistré) : `p-admin` Administrateur (tout au plus haut niveau), `p-rh` RH (tout sauf Administration), `p-manager` Manager (lecture des registres, auteurs du SST visibles, Santé & Visites en lecture), `p-agent` Agent (lecture des registres, dépôt au registre SST), `p-preventeur` (déclarer un AT/MP ; Dossiers AT/MP, Analyse d'accident, Urgences en gestion ; Santé & Visites en lecture — les droits en plus de `PREV1` avant), `p-representant` Représentant du personnel (Dialogue social : participer). Un profil personnalisé (`p-` + identifiant tiré au hasard) a « aucun » pour tout module non coché ; il se supprime tant qu'aucun compte ne l'a. **Libellé et pastille** affichés en haut des pages = ceux du **premier** profil du compte (les préréglages gardent « Compte RH »/« RH », « Compte Agent »/« AG »…) ; les autres profils vont dans une infobulle.

**Ce que fait chaque niveau** — la correspondance page par page est dans les pages elles-mêmes (`const D = VigieDroits.pour(session)`, puis `D.peut("module", "niveau")` ; plus aucun `role ===` dans une page) :
- Pages « module » : `consulter` ouvre la page (sinon redirection vers le tableau de bord), le niveau d'écriture montre les boutons (`gérer` ; `participer` au Dialogue social ; `rédiger` à la Base documentaire — dont la lecture reste ouverte à tout profil préréglé).
- Registre AT/MP : `gérer` = tout (filtres, import/export, modification, colonnes d'identité et de situation) ; `déclarer` = la page de saisie et le lien « Nouvelle déclaration » du registre (sans import, export ni « Vider le journal de saisie », réservés à `gérer`), sans modifier l'existant ; `consulter` = la vue réduite. Registre SST : `répondre` = répondre, importer, clôturer, supprimer ; `auteurs` = voir qui a écrit ; `déposer` = déposer une observation. Dialogue social : `direction` = répondre en direction et clôturer (le drapeau « direction » des messages).
- Document unique : les filtres Collectivité/Service s'affichent pour tout lecteur (aujourd'hui masqués au seul agent : changement voulu, rien de plus n'est transmis).

**Compatibilité avec l'ancien format.** Un compte sans `profils` (rôle + `modulePermissions`) et une session sans `droits` (session ouverte avant la mise à jour, harnais de test) se résolvent à la volée en **exactement les mêmes droits qu'avant** : préréglage de leur rôle, plus leurs permissions de module (`read` → consulter, `write` → gérer ; `atmp-declare` → déclarer ; `documentation: write` → rédiger ; `dialogue-social: write` → participer). Une table `VigieDroits.ANCIENNES` en fait la correspondance. À la première ouverture d'**Administration**, les comptes à l'ancien format sont **convertis** : préréglage du rôle, plus « Préventeur » si leurs permissions sont exactement celles-là, sinon un profil « Droits particuliers — <identifiant> » partagé par les comptes qui ont les mêmes ; ligne d'audit « Comptes convertis… ». `role` et `modulePermissions` restent sur la fiche (restauration d'une sauvegarde, retour arrière) mais sont ignorés dès que `profils` existe.

**Garde anti-verrouillage.** Il doit toujours rester un compte actif, non anonymisé, qui puisse administrer : Administration refuse (profil modifié, compte modifié/désactivé/supprimé) ce qui l'enfreindrait ou vous retirerait votre propre droit d'administrer, et le **serveur** le refuse aussi par l'API (403, `comptes.gardeAdmin`).

**Session.** `login.html` (mode navigateur) et `serveur/comptes.js` (`sessionDePage`) la construisent : `{ user, role (indicatif), email, services, modulePermissions (ancien format), anonymise, profils: [noms], droits: { module: niveau }, compte: { libelle, pastille } }`. Sur le serveur elle est reconstruite à **chaque requête** depuis la fiche du compte et les profils : modifier un profil s'applique à la requête suivante, sans reconnexion (en mode navigateur : à la prochaine connexion).

- **Compte anonymisé** (2026-09-25, réponse Q16) : case `u.anonymise` dans Administration, copiée dans la session. En mode serveur, `serveur/anonymisation.js` ne transmet à ce compte aucune donnée de santé (les cinq clés `sensible` autres que le registre AT/MP retirées ; `vigie_hse_dataset` réduit à id, collectivité, service, mois, année, type, arrêt, jours d'arrêt, famille de risque — y compris dans une réponse de conflit) ; il n'y peut qu'ajouter, greffé sur le registre complet. En mode navigateur, seul l'affichage du module l'est (avertissement à l'écran).
- **Un nouveau module** s'ajoute **une fois** : au catalogue `MODULES` d'`assets/droits.js`, à la liste `MENU` et à `voir()` de `assets/menu-lateral.js`, à la table `REGLES` de `serveur/droits.js` (un test refuse une clé de `VigieStore.CLES` sans règle) et, s'il a des registres sensibles, à `serveur/lecture.js`. Un module ajouté plus tard ne s'ouvre à personne tout seul : un profil personnalisé a « aucun » pour tout ce qu'il ne connaît pas ; seuls les préréglages reçoivent la valeur de la graine.

- **En mode serveur (P1b, 2026-09-24), ces règles sont aussi appliquées par le serveur** (`serveur/droits.js`) : un compte ne peut plus écrire par l'API ce que son écran ne lui permet pas. Tout changement de règle dans une page doit être répercuté dans `droits.js` — sinon le serveur refuse et la page affiche « votre compte n'a pas le droit… » (c'est d'ailleurs ainsi qu'un écart se repère).
- **Santé & Visites réservé à l'encadrement (question 17, 2026-09-29)** : manager (ses services), RH et administrateur ; un agent est renvoyé au tableau de bord, sauf s'il a la permission « sante-visites » (lecture ou écriture, ex. `PREV1` en lecture) ; le lien `navSanteVisites` du menu ne s'affiche que pour ces trois rôles et ces comptes (23 pages ; Administration, réservée à l'administrateur, garde son lien), et le serveur ne lui transmet ni `vigie_hse_visites` ni `vigie_hse_rdv_medicaux`.
- **Droits de lecture (2026-09-27)** : en mode serveur, ce qu'un compte **reçoit** suit aussi ses écrans (`serveur/lecture.js`, tableau au §4 quinquies de `PLAN-MISE-EN-PRODUCTION.md`). Une page qui se met à afficher un champ ou un registre de plus pour un rôle doit être répercutée dans `lecture.js` — sinon l'information manque à l'écran, sans erreur (c'est ainsi qu'un écart se repère). Chaque ligne du journal de saisie AT/MP porte désormais un `id`. **Depuis le 2026-10-01, un registre que UNE seule page lit n'est plus transmis à un compte qui n'a pas le niveau « consulter » du module de cette page** (table `PAGE_UNIQUE` de `serveur/lecture.js` : accueils, modèles et délai d'accueil au poste ; expositions et paramètres de la Pénibilité ; questions et réunions du Dialogue social ; documents et types de la Base documentaire ; stock et lavages des EPI ; trames d'Inspection / Audit ; modèles de convocation de Santé & Visites) : un profil sans accès à un module ne reçoit plus ses données, pas seulement son lien. Les registres que d'autres pages lisent aussi (tableau de bord, Reporting, Plan d'actions, sélecteur d'agents, fiches utiles) restent transmis, sinon leur affichage se vide — **un registre nouveau qu'une seule page lit s'ajoute à `PAGE_UNIQUE`** (relever d'abord qui le nomme : `grep` de la clé dans les pages et les composants).
- **Périmètre (P1c, 2026-09-25)** : en mode serveur, un compte dont `services` ne contient pas `"*"` ne reçoit plus que les enregistrements de ses services (`serveur/perimetre.js`) — le filtre `isScoped` des pages reste, il ne voit simplement plus rien d'autre. Un enregistrement nouveau d'un module doit donc porter son `service` pour être rangé dans le bon périmètre ; sans `service`, il est transmis à tous. Reporting et les indicateurs du Dialogue social affichent alors « Périmètre : vos services (…) ». **En mode navigateur aussi (2026-10-07)**, l'écriture d'un compte limité est greffée sur le registre complet par `VigieStore` (`assets/stockage.js`, même algorithme que `greffer` du serveur) : sans cela, la page enregistrait sa liste filtrée et effaçait les autres services (`BUGS-CONNUS.md`).
- Pattern d'accès dans le code de chaque page : `const D = VigieDroits.pour(session);` puis `const canX = D.peut("module", "consulter"); const canXWrite = D.peut("module", "gerer");` — un module de plus = une ligne au catalogue, pas un nouveau test de rôle.
- **Menu** (`voir()` d'`assets/menu-lateral.js`, sur les niveaux de `VigieDroits`) : chaque lien se montre ou se cache individuellement, selon le niveau « consulter » de son module (ou le niveau de saisie : « Déclarer un AT/MP » demande `déclarer`, « Évaluer un risque » demande `gérer` au Document unique). Avant les profils : les liens dont la visibilité dépend d'une permission granulaire (pas seulement du rôle) ont chacun leur propre `id` et sont masqués/affichés individuellement (`display:none` par défaut, révélé par JS), plutôt que la section entière — évite d'afficher un lien qu'un détenteur d'une seule des permissions ne pourrait pas utiliser (ex. "Déclarer un AT/MP" et "Évaluer un risque" dans la section "Espace RH" sont maintenant deux toggles indépendants, pas un seul pour toute la section).

## 9. Pattern architectural clé : fusion seed + stockage ("always-merge")

**Le pattern le plus important à comprendre avant de toucher au code.** Chaque module a un tableau `SEED_XXX` codé en dur (les données de démo/réelles initiales) et une fonction `loadDataset()` (nom variable selon fichier) qui, à chaque chargement de page :

1. Lit ce qui est déjà en `localStorage` (peut être vide, partiel, ou modifié par l'utilisateur).
2. Pour chaque enregistrement du `SEED`, utilise la version stockée si elle existe (id identique), sinon prend la version seed telle quelle.
3. Ajoute à la suite tout enregistrement stocké dont l'id n'est PAS dans le seed (= créé par l'utilisateur).
4. Réécrit immédiatement ce résultat fusionné dans le `localStorage`.

**Pourquoi c'est comme ça et pas plus simple ("si vide, on seed") :** une version précédente ne réenclenchait le seed que si le stockage était totalement vide, ce qui provoquait des bugs difficiles à diagnostiquer (données "disparues" après un test précédent qui avait laissé un état partiel en `localStorage`). Le pattern "always-merge" est auto-réparateur : peu importe l'état du navigateur, les données seed réapparaissent toujours, tout en préservant les modifications/ajouts de l'utilisateur. **Ne jamais revenir à un pattern "seed si vide".**

Les IDs des seeds sont **stables et déterministes** (ex. `pa-<id du risque DUERP source>` pour une action auto-générée, hash du nom+service pour une fiche de visite) — c'est ce qui permet à la fusion de fonctionner sur plusieurs rechargements sans dupliquer ni perdre des données.

## 10. Système de design

- Palette pastel douce définie en custom properties CSS (`--bg`, `--surface`, `--accent`, `--success`, `--warning`, `--danger`, `--critical`, etc.), avec équivalents clair/sombre.
- Support thème clair/sombre via `@media (prefers-color-scheme: dark)` + attribut `data-theme` : le triptyque `:root` / media query / `[data-theme]` vit dans **`assets/jetons.css`** (depuis le 2026-10-01) ; une page n'y ajoute que ses jetons propres.
- Layout sidebar (250px, rétractable au survol sur desktop ≥981px, tiroir off-canvas sur mobile) + topbar (60px, sticky).
- Composant récent : en-têtes de page compacts et sticky (`.page-summary`) fusionnant logo/titre/description/KPI sur une ligne — en cours de généralisation à tous les modules (voir §12, travaux en cours).
- Le CSS est partagé en couches, dans l'ordre où les pages les lient : `assets/polices/polices.css` (polices), `assets/jetons.css` (jetons de couleur), `assets/commun.css` (règles communes, 23 pages), puis le `<style>` de la page (ce qui lui est propre) et `assets/mobile.css` (réglages téléphone communs). Une évolution du design system se fait dans la couche concernée, une seule fois ; le tableau de bord, la connexion et la vitrine gardent un CSS plus propre à eux (voir §6).

## 11. Pièges connus / leçons apprises

- **Artifact hébergé = localStorage cassé.** Toujours tester en ouvrant les fichiers `.html` en local, jamais via un lien Artifact.
- **Parsing Excel sans logiciel installé** : ce projet a été construit sur une machine sans Excel/LibreOffice/Python. Les fichiers `.xlsx` ont été parsés en PowerShell pur (dézippage + parsing XML `xl/sharedStrings.xml` / `xl/worksheets/sheetN.xml`). Les `.xls` (format binaire OLE2 ancien) sont **illisibles** avec cette méthode — il faut demander à l'utilisateur de les réenregistrer en `.xlsx`.
- **Encodage PowerShell** : toujours lire/écrire les fichiers avec `[System.IO.File]::ReadAllText/WriteAllText` + `New-Object System.Text.UTF8Encoding($false)` — `Get-Content`/`Out-File` par défaut corrompent les accents français ("Ã©" etc.).
- **Fichiers HTML volumineux** : certains fichiers dépassent la limite de tokens de l'outil de lecture à cause des tableaux `SEED` massifs. Technique de contournement : créer une copie "lisible" avec les lignes de plus de ~2000 caractères tronquées, la lire, éditer le vrai fichier séparément. Pour insérer un gros tableau de données dans un nouveau fichier, utiliser un placeholder texte (`__SEED_XXX__`) écrit via l'outil d'édition, puis le remplacer par le vrai contenu via un script PowerShell (`.Replace()`) — évite de faire transiter des dizaines de milliers de caractères de données à travers le contexte de conversation.
- **Édition en masse par regex non ancrée = risque de corruption.** Un remplacement regex trop large a un jour corrompu des liens `<a>` et injecté un `<symbol>` égaré dans un `<defs>` non lié, en cherchant à modifier toutes les sidebars en une passe. Depuis : édits ciblés fichier par fichier, avec vérification systématique de l'équilibre des accolades/parenthèses/crochets JS après coup (voir §13).
- **Texte d'enregistrement injecté dans `innerHTML`.** Jusqu'au 2026-09-23, les seize pages qui affichent des données inséraient le texte de leurs enregistrements tel quel dans un gabarit HTML : un libellé contenant une balise était rendu comme une vraie balise, avec ses attributs événementiels. Les données venant des imports Excel, des formulaires et des référentiels, rien n'était sûr. Toutes ces pages déclarent maintenant `const esc = (s) => …` en tête de script et l'appliquent à chaque interpolation de texte. **Trois pièges** repérés à cette occasion : les colonnes déclarées hors gabarit (`render:r => r.champ || ""`), les fonctions de date qui renvoient la chaîne d'origine quand la valeur n'est pas une date ISO, et les ternaires qui concatènent un champ. À l'inverse, **ne pas** échapper les messages du journal d'audit, des `confirm()` et des affectations `textContent`.
- **Dates « AAAA-MM-JJ » calculées en UTC.** `new Date("2026-01-20")` vaut minuit **UTC**, et `toISOString()` repasse en UTC. En France (UTC+1/+2) cela donne la veille entre minuit et 2 h du matin, et — plus grave — après un calcul de mois qui franchit le passage à l'heure d'été, la veille **à toute heure** : jusqu'au 2026-09-23, les échéances de quatre modules et le renouvellement des EPI s'affichaient un jour trop tôt (2026-01-20 + 6 mois → 2026-07-19). Pour lire, écrire ou calculer une date du jour, passer par `assets/dates-locales.js` (ou un équivalent local comme `parseLocal`/`addDays` d'`accueil-poste.html`). Depuis le 2026-09-23, **plus aucun** `toISOString().slice(0,10)` ne reste dans les pages (61 remplacés — voir `BUGS-CONNUS.md`) ; `toISOString()` entier reste correct pour un **horodatage** (journal d'audit, `maj`), qui est un instant et non une date calendaire.
- **Pas de balise `viewport` = pas de téléphone.** Jusqu'au 2026-09-29, aucune page n'avait `<meta name="viewport">` : un téléphone les affichait comme un écran de 980 px réduit (texte minuscule — la remarque « titres et menu trop petits » de la checklist §5), et **aucune règle `@media (max-width:…)` ne s'appliquait sur un vrai téléphone** ; seul un navigateur d'ordinateur rétréci les déclenchait. Chaque page commence désormais par `<meta charset="utf-8">` et `<meta name="viewport" content="width=device-width, initial-scale=1">` — **toute nouvelle page aussi**.
- **Jamais « Ville » ni « Agglomération » en dur** (depuis le 2026-09-30). Une nouvelle page ou un nouveau formulaire passe par `VigieOrga` (`assets/organisation.js`) : listes marquées `data-org`, libellé `data-org-libelle`, `VigieOrga.de(r)` pour afficher, `VigieOrga.actuel(r.collectivite) === col` pour filtrer, `VigieOrga.reconnaitre()` à l'import, `VigieOrga.libelle()` en en-tête d'export. Seules exceptions : les corrections de données anciennes (« déchetterie → Agglomération ») et les données de démonstration, ramenées par `anciensNoms`. Test de non-régression : photo-org.js (outil du scratchpad, hors dépôt) — 96 visites, avant/après, identiques avec la configuration par défaut.
- **Jamais « VIGIE HSE » ni « Soft Tech » en dur dans un texte nouveau** (depuis le 2026-10-01). Le nom du produit est un réglage (`assets/marque.js`) : dans le HTML, `<span data-marque="nom">VIGIE HSE</span>` (le texte d'origine reste, c'est ce que voit un poste sans marque) ; dans un script, `VigieMarque.nom()` (repli « VIGIE HSE » si le composant manque, comme dans `assets/stockage.js` qui se charge avant lui). Deux leçons : (1) pour qu'un réglage de couleur gagne sur les `:root` de 26 pages quel que soit l'endroit où son script est inséré, on le déclare avec un sélecteur plus précis (`html:root`) plutôt que de compter sur l'ordre du document ; (2) un texte remplacé après coup clignote (le nom d'origine s'affiche une fraction de seconde) : on le masque (`visibility:hidden`) jusqu'au `DOMContentLoaded`, et seulement quand une marque est réglée. Le contraste du texte blanc des boutons sur la couleur choisie n'est qu'**avertissé** (seuil 2,5:1, plus clair que ce que l'écran d'origine accepte déjà : ses deux couleurs sont à 3,0 et 2,7) : le choix reste à l'administrateur.
- **« Collectivité » a deux sens** (2026-09-30) : l'**employeur** (« référentiel de la collectivité ») et l'**entrée de l'organisation** (Ville, Agglomération, Site…). Le premier passe par `VigieOrga.mots()` (« l'entreprise » en secteur entreprise), le second par `VigieOrga.libelle()` (le mot choisi dans Administration). Deux restes de la bascule d'organisation l'ont montré : le message d'import des heures de Gestion RH et le libellé du champ `collectivite` de l'export « Données d'une personne » (`libelles-champs.js`) disaient « collectivité » quel que soit le mot choisi. Un **métier** qui contient « agent » (« Agent d'entretien », « agent de maîtrise ») n'est pas une personne au sens du secteur : ne pas le marquer. Test : photo-mots.js (scratchpad) — 98 visites identiques à `main` en secteur collectivité ; `restes` liste ce qui dit encore « agent » en secteur entreprise (données de démonstration comprises).
- **Styles et icônes communs** (2026-09-30) : déplacer une règle CSS d'une page vers `assets/commun.css` change son rang dans la cascade (la feuille commune passe avant **toutes** les règles de la page) ; une règle de la page qui la précédait et visait les mêmes éléments gagne alors au lieu de perdre. Le seul contrôle probant est le **style calculé de chaque élément**, avant / après, dans un vrai navigateur (outil empreinte-navigateur.js du scratchpad : chaque page dans un cadre, bureau et téléphone, clair et sombre). Deux pièges de mesure : Chrome n'énumère pas les variables CSS dans le même ordre d'une origine à l'autre (trier les propriétés), et des pages tirent des identifiants au hasard (ne pas les compter) ; vider le stockage des deux origines avant de mesurer. Pages sans `<body>` explicite : un `<script>` placé après `<style>` s'exécute encore dans `<head>`, sans `document.body` — d'où l'insertion du sprite par `VigieMenu.init`.
- **Aligner une page sur `commun.css` / `jetons.css`** (2026-10-01). Ne retirer d'une page que ce qui est **identique** à la feuille commune, et réduire une règle qui diffère à **sa seule déclaration d'écart** : laisser une règle entière en local alors qu'elle existe aussi dans la feuille commune change l'ordre de la cascade (la feuille commune passe avant tout le `<style>` de la page) et peut faire gagner une règle qui perdait (`.mono` de la page, placée avant `.ps-kpi-value`, perdait ; copiée en entier après lui, elle gagnait — la mesure l'a vu sur les KPI de Document Unique et du Registre AT/MP). La preuve est le style **calculé** de chaque élément, avant / après, dans un vrai navigateur : un petit serveur sert le dépôt à la racine et la version de référence (`git archive`) sous `/avant/` sur **le même port**, et une fonction collée dans le panneau compare, page par page, les deux pages chargées dans des cadres (bureau 1280 et téléphone 390, clair puis sombre forcé par `data-theme`, comptes administrateur puis agent). Deux pièges : le premier chargement d'une page amorce ses données (stock EPI…) — **rejouer une page dont le nombre d'éléments diffère** avant de conclure à un écart de style ; et un jeton **gagné** par une page qui ne le déclarait pas (aucun usage) apparaît comme une différence si l'on compare aussi les variables CSS : pour ces pages (Administration, saisie RH, connexion, vitrine) on compare les seules propriétés réelles.
- **`<!doctype html>` en première ligne, et les compensations du mode « quirks ».** Jusqu'au 2026-09-29, aucune page n'avait de doctype : toutes étaient rendues en mode « quirks » (`document.compatMode === "BackCompat"`). Chaque page commence désormais par `<!doctype html>`, puis `<meta charset>` et `<meta name="viewport">` (mode standard, `CSS1Compat`) — **toute nouvelle page aussi**. Pour que rien ne bouge, le `<style>` des pages concernées reproduit trois comportements du mode « quirks », sous un commentaire qui le dit : `form{ margin-bottom:1em; }` (20 pages), `textarea{ vertical-align:top; }` (14 pages : pas de jour sous une zone de texte seule sur sa ligne), et quelques règles ciblées pour une ligne qui ne contient qu'un élément sans texte, que le standard rehausse à la hauteur de ligne du parent (`.cat-chip` du Registre AT/MP, `.feed-clear` des deux saisies, `.reset-row` de la vitrine, cellules d'étiquettes et libellé `#uServicesWrap` de l'Administration). **Ne pas les retirer sans refaire la comparaison**, et penser au même piège dans une nouvelle page : un bouton, une pastille ou une zone de texte seul sur sa ligne prend quelques pixels de plus en mode standard. Méthode de comparaison (outils de relevé et de comparaison dans le scratchpad de la session, hors dépôt, à réécrire au besoin) : Edge sans fenêtre piloté par le protocole DevTools, horloge et `Math.random` figés, transitions coupées, une passe de chauffe pour remplir le stockage, puis position, taille, police et styles calculés de chaque élément + feuilles de style + capture, à 1 400 et 375 px — et une seconde passe qui force l'affichage de tout élément masqué (fenêtres de saisie, onglets). Écarts restants et acceptés : `BUGS-CONNUS.md`.
- **Dates importées lues dans l'ordre américain.** Jusqu'au 2026-10-06, une date écrite en texte « 01/09/2026 » s'importait au **9 janvier** : dans un CSV (Excel français, LibreOffice), SheetJS devine les dates dans l'ordre mois/jour et rend un objet Date ; dans un `.xlsx`/`.ods` où la date est du texte, les fonctions d'import des pages prenaient le premier nombre pour le mois. Un jour au-delà de 12 (« 25/09/2026 ») s'enregistrait « 2026-25-09 », date impossible que `VigieDates.lire` décale de deux ans. Seules les vraies dates de tableur passaient. Désormais : `VigieImport.lireClasseur` rend leur texte aux cellules qu'un CSV avait converties en date, et **toute date lue dans un fichier passe par `VigieDates.depuisImport`** (JJ/MM/AAAA à la française, date impossible refusée). Un nouvel import de date : utiliser ce lecteur, jamais `String(cellule)` (une vraie date Excel donnerait « Tue Sep 01 2026 … ») ni `new Date(texte)` (ordre américain).
- **Export Excel d'une feuille vide sans en-têtes.** `XLSX.utils.json_to_sheet([])` produit une feuille **sans ligne d'en-têtes** : un registre vide s'exportait en fichier blanc, inutilisable comme modèle d'import. Chaque export passe désormais la liste de ses colonnes (`json_to_sheet(lignes, { header: [...] })`) ; en ajoutant une colonne à un export, l'ajouter aussi à cette liste (sinon elle manquera seulement quand la feuille est vide).
- **Échapper aussi les identifiants, les valeurs d'attribut et les listes déroulantes** (revue du 2026-09-30). Le premier passage d'échappement avait laissé : `data-id="${r.id}"` (un identifiant vient d'un import ou, en mode serveur, d'un compte qui ne peut que déclarer — il sortait de l'attribut et exécutait son code chez le RH qui ouvre le registre), les 17 listes `<option value="${s}">` de services (un nom contenant `"` coupait la valeur : le filtre ne retrouvait plus rien), et des échappements faits main qui ne traitaient que le guillemet. Règle : **`esc()` sur toute valeur, y compris un identifiant et un attribut** ; un lien issu d'une donnée ne devient un `href` qu'en `http(s)` (`safeUrl`, Base documentaire, Produits chimiques, tableau de bord) ; jamais de sélecteur CSS bâti sur une donnée (`querySelector('[value="' + x + '"]')` plante sur un `"`). **Piège de test** : `innerHTML` sur un `<select>` ignore `<img>` et `</select>`, si bien qu'une sonde qui cherche un élément injecté ne voit rien — chercher aussi l'attribut parasite. Sonde générale : toutes les pages × quatre comptes, données de démonstration et un enregistrement synthétique par registre, chaque texte piégé (référentiels et organisation compris).
- **Menu latéral : une seule source** (2026-09-30). Recopié dans 24 pages, il avait dérivé (liens absents, liens interdits montrés, épingle morte) : `assets/menu-lateral.js` le construit désormais pour toutes. Un nouveau module s'ajoute **une fois** à `MENU` et `voir()` — plus de « rollout » de lien page par page.
- **Les droits sont une donnée, pas du code** (2026-10-01). Quatre rôles codés en dur plus onze permissions ajoutées module par module avaient fini par peser ≈ 89 contrôles dans 28 fichiers ; un module de plus voulait dire un test de plus partout. `assets/droits.js` est maintenant la seule définition (catalogue de modules à niveaux ordonnés + profils), lue par les pages **et** par le serveur : une page ne teste plus `role ===`, elle demande `D.peut("module", "niveau")`. Deux garde-fous qui ont servi : (1) un test différentiel compare l'ancien serveur (copie de `main`) au nouveau sur chaque registre × une matrice de comptes à l'ancien format — 24 948 contrôles identiques, hors RH sur le journal d'audit (« complet » devenu « ajout », sans effet : le journal est retiré à ce compte et ses écritures sont déjà greffées comme de simples ajouts) ; (2) l'ancien format reste lu à la volée, donc une session ouverte avant la mise à jour ou un harnais qui fabrique `{role, modulePermissions}` à la main continue de fonctionner. Piège à retenir : **le droit « complet » sur un registre ne doit jamais dépendre d'une règle générale** — une clé de `VigieStore.CLES` sans règle explicite dans `serveur/droits.js` serait refusée à tous sauf à l'administrateur ; un test le vérifie.
- **Serveur sous Windows : contrôler le vrai chemin d'un fichier, pas l'adresse demandée** (2026-09-30). Le filtre « ni `serveur/`, ni dossier caché » comparait des noms : `/SERVEUR/comptes.js` (casse) et `/CLAUDE~1/settings.json` (nom court 8.3 de `.claude`) passaient, sans connexion. `fichier()` résout désormais le chemin réel (`fs.realpathSync.native`) avant de juger. Même famille : un contrôle « ajout seulement » qui indexe par identifiant doit aussi refuser qu'un identifiant existant revienne une fois de plus (copie modifiée glissée devant l'original).
- **Délégation à des agents en arrière-plan** : un agent a un jour continué à travailler ~2h après la fin de sa tâche assignée, en inventant lui-même des suites non demandées, jusqu'à échouer sur une limite de débit. Depuis, toute délégation à un agent en arrière-plan (`fork`) est bornée explicitement ("fais exactement ceci, puis ARRÊTE-TOI, n'invente rien au-delà"), et son travail est systématiquement re-vérifié indépendamment (pas seulement son propre rapport) avant d'être présenté comme terminé.

## 13. Comment vérifier qu'un fichier n'est pas cassé après édition

Depuis le 2026-09-18 environ, Node est disponible et c'est la méthode de référence :

1. **Syntaxe** : passer chaque bloc `<script>` inline de chaque page modifiée à `new Function(...)` sous Node (une erreur de syntaxe lève une exception qui nomme le bloc), et chaque fichier de `assets/`.
2. **Balises de composants** : vérifier que chaque page qui utilise un composant partagé (`VigieTri`, `VigieDates`, `VigieImpression`…) charge bien son `<script src="assets/…">`, et que `dates-locales.js` précède `echeance.js`.
3. **Comportement** : harnais jsdom (pages réellement exécutées, avec les vrais fichiers `DATATEST/` lus par le vrai SheetJS, une session de compte de test injectée). Ils vivent hors du dépôt, dans le scratchpad de la session — liste et rôle de chacun dans `POINT-DE-REPRISE.md`. Toujours éprouver un harnais sur un cas qui doit échouer avant de croire son « zéro erreur ». Un script dont le corps est une fonction `async` relaie son erreur (`.catch` → message et code non nul) : sinon un capteur `unhandledRejection`, posé pour les erreurs des pages, l'avale et le script finit avec le code 0.
4. **À l'œil** : le panneau navigateur de l'application ouvre un fichier local sans stockage ; servir le dossier en `http://localhost:8765` avec `Documentation/outils/serveur-local.js` (configuration « vigie-local » de `.claude/launch.json`) pour tester une page avec une session.

L'ancienne méthode — compter accolades, parenthèses et crochets de chaque bloc `<script>` par une regex PowerShell — reste un dépannage quand Node manque ; un déséquilibre n'y est pas toujours une vraie erreur (une chaîne contenant `" ("` fausse le compte).
